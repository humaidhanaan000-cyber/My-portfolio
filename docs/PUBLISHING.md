# Publishing AIBA — from the GitHub repository to a website people can open

This is the "how do I get a real link" document. Read the first section if you
are unsure why a GitHub repository is not itself a website.

---

## 0. What GitHub does and does not do

| | GitHub | A host (VPS, Render, Railway, Fly, your own server) |
| --- | --- | --- |
| Stores the code | ✅ | — |
| Shows the source / history / issues | ✅ | — |
| Runs a Node.js web server | ❌ | ✅ |
| Runs a database | ❌ | ✅ |
| Runs the background worker + cron scheduler | ❌ | ✅ |
| Gives you a public `https://…` address for the app | ❌ | ✅ |

**GitHub Pages cannot host AIBA.** Pages serves static files only. AIBA needs a
Node.js process (API routes, sessions), a database, and long-running worker and
scheduler processes. A static export would lose login, approvals, budgets, jobs
and revenue tracking — i.e. everything that makes it an agent rather than a
mockup. So: **GitHub stores the blueprint, a host runs the engine.**

Two addresses exist, and they are different things:

- the **code link** — `https://github.com/humaidhanaan000-cyber/My-portfolio`
- the **website link** — created by one of the methods below, e.g. `https://aiba.yourdomain.com`

> Right now the app **is** running and clickable: it is the Arena live preview
> attached to this session (`https://3000-<sandbox>.e2b.app`). That preview is
> temporary — it stops when the sandbox does. For a permanent link, keep reading.

## 1. Method A — your own server (recommended: full functionality)

Best when you want the worker, the scheduler and the database all on one box you
control, which is what "runs while my PC is off" actually requires. Any €4–6/month
VPS is enough (1 vCPU / 1 GB RAM / 20 GB disk).

```bash
# on the server, as a normal user with sudo
sudo apt update && sudo apt install -y docker.io docker-compose-v2 git
sudo usermod -aG docker "$USER" && newgrp docker      # log out/in after this

git clone https://github.com/humaidhanaan000-cyber/My-portfolio.git aiba
cd aiba
git checkout main            # after you merge the pull request

cp .env.example .env
openssl rand -hex 32          # put this in AUTH_SECRET
openssl rand -hex 24          # put this in POSTGRES_PASSWORD
nano .env                     # set APP_URL=https://your-domain, COOKIE_SECURE=true

docker compose up -d --build
docker compose ps             # every service should say "healthy"
```

Then put a domain in front of it (Free DNS + Let's Encrypt):

```bash
sudo apt install -y nginx certbot python3-certbot-nginx
sudo certbot --nginx -d your-domain.com      # follow the prompts
```

nginx snippet (details in `docs/DEPLOYMENT.md §5`):

```nginx
server {
  listen 80;
  server_name your-domain.com;
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }
}
```

Done: `https://your-domain.com` is now the app, running continuously. Verify with
`curl -s https://your-domain.com/api/health | jq '.status'` → `ok` (or `degraded`
until you add an AI key), and sign in with the administrator account
(`SEED_ON_START=true` creates `admin@aiba.local`; change that password
immediately).

## 2. Method B — Render (no server administration; blueprint included)

The repository contains `render.yaml`. Render reads it and creates the web
service, the worker, the scheduler, PostgreSQL and Redis for you.

1. Push the repository to GitHub (already done) and merge the work into `main`
   (or set `branch:` in `render.yaml` to the branch you want to deploy).
2. In Render: **New +** → **Blueprint** → choose the repository → **Apply**.
3. Render asks for the values marked `sync: false` — at minimum `APP_URL`. Leave
   the optional AI / email / payment keys empty for now; the app starts without
   them and reports `DEGRADED` with the reason.
4. When the web service is live, copy its URL (e.g.
   `https://aiba-web.onrender.com`), set it as `APP_URL`, and let the service
   redeploy. **`APP_URL` must match the address people use**, otherwise emails
   and session cookies point at the wrong origin.
5. Verify: open the URL → register an account → finish onboarding → the dashboard
   should show agents and a running queue.

Notes and gotchas, stated honestly:

- `AUTH_SECRET` is generated by Render (`generateValue: true`) — never edit it by
  hand once users exist; changing it signs everybody out.
- **Asset storage is ephemeral on Render** because the three containers do not
  share a disk. Set `STORAGE_DRIVER=s3` plus S3/R2 credentials
  (`docs/INTEGRATIONS.md §6`) if you want generated files to survive a redeploy.
- The free instance plans sleep after inactivity, which stops the "always on"
  promise and pauses the scheduler. Use the paid `starter` plans for a real
  agent; scale the worker (`numInstances`) if the queue backs up.
- Exactly one scheduler instance — it holds the leader lock.
- Keep `ENABLE_INLINE_JOBS=false` and `ENABLE_SCHEDULER=false` on the web service,
  as the blueprint already does, so the web process does not duplicate work.

## 3. Method C — Railway, Fly.io, or any Docker host

**Railway** (great DX, Postgres + Redis one click):

```bash
npm i -g @railway/cli
railway login
railway init
railway add --plugin postgresql
railway add --plugin redis
# Create three services from the same repository: web (default command),
# worker (`npm run worker`), scheduler (`npm run scheduler`)
railway up
```

Set the same variables as the blueprint above, then generate a public domain in
the service settings.

**Fly.io**:

```bash
fly launch --no-deploy          # detect the Dockerfile, keep the app name
fly postgres create --name aiba-db && fly postgres attach aiba-db
fly redis create                # or Upstash via fly ext
fly secrets set AUTH_SECRET=$(openssl rand -hex 32) APP_URL=https://<app>.fly.dev COOKIE_SECURE=true
fly deploy
fly scale count web=1 worker=1 scheduler=1     # or run worker/scheduler as separate apps/process groups
```

**Any other Docker host** (Coolify, Kamal, Kubernetes, a NAS): build the image
(`docker build -t aiba:1.0.0 .`) and run three processes from it —
`node server.js`, `npm run worker`, `npm run scheduler` — pointing them at the
same PostgreSQL and Redis. That is exactly what `docker-compose.yml` does.

## 4. Method D — Vercel (works for the UI, not for the agent)

Vercel runs the Next.js app well, and with a hosted Postgres (Neon, Supabase)
the dashboard, API, auth, approvals, budgets, revenue and reports all work.
What Vercel **cannot** give you:

- a long-running **worker** process — jobs would sit in `queued` forever;
- a long-running **scheduler** — the recurring research/monitoring/report jobs
  would never be enqueued;
- a writable local disk — use S3-compatible storage.

So on Vercel you must run the worker and scheduler somewhere else (a small VPS,
a Render background worker, or a Fly machine) pointed at the same `DATABASE_URL`
and `REDIS_URL`. If you do not want two hosting providers, use Method A or B —
they are the configurations this project is actually tested against.

## 6. Which method should you pick?

| Your situation | Use |
| --- | --- |
| "I want it running 24/7 on my own box, full control, cheapest" | **A — VPS + Docker Compose** |
| "I do not want to touch a server, but I want the worker to run" | **B — Render blueprint** |
| "I already live in Railway/Fly" | **C** |
| "I just want the UI online to look at it" | **D — Vercel**, accepting no background jobs |

Whatever you choose, the fixed order is: publish code → provision database →
set secrets (`AUTH_SECRET`, `APP_URL`, `COOKIE_SECURE=true`) → start web +
worker + scheduler → check `/api/health` → register the first account and change
the admin password → then work through `docs/LAUNCH_CHECKLIST.md`.

## 7. Seven more ways to open the console in a browser

Every method below runs the real application (no mockup). They differ in *where*
the Node processes and the database live. "Fully autonomous" means the worker and
scheduler keep running 24/7; the others run while the machine or session is alive.

| # | Method | Where it runs | Browser address | Needs installing something? | Fully autonomous |
| --- | --- | --- | --- | --- | --- |
| 1 | Start file on your PC (`start-aiba.bat/.command/.sh`) | your computer | `http://localhost:3000` | Node.js 22 | ⏸ while the PC is on |
| 2 | Docker Desktop / Compose | your computer | `http://localhost:3000` | Docker Desktop | ⏸ while the PC is on |
| 3 | **LAN / phone on the same Wi-Fi** | your computer | `http://<pc-ip>:3000` | Node.js 22 | ⏸ while the PC is on |
| 4 | **Temporary public link (Cloudflare Tunnel)** | your computer | `https://<random>.trycloudflare.com` | Node.js + cloudflared | ⏸ while the PC is on |
| 5 | **GitHub Codespaces** | GitHub cloud | Codespaces "Ports → Open in browser" URL | nothing | ⏸ while the Codespace runs |
| 6 | **Google Cloud Shell** | Google cloud | Cloud Shell "Web preview" URL | nothing (Google account) | ⏸ while the session runs |
| 7 | **Replit** | Replit cloud | Replit webview URL | nothing | ⏸ (free tier sleeps) |
| 8 | VPS + Docker Compose (§1) / Render (§2) / Railway / Fly (§3) | cloud | your own `https://` domain | nothing locally | ✅ 24/7 |

### Method 3 — open it from your phone on the same Wi-Fi

The app already listens on `0.0.0.0`, so any device on your network can reach it.

1. Start it on the computer: `npm run agent` (or the start file).
2. Find the computer's local IP:
   - Windows: `ipconfig` → *IPv4 Address* (e.g. `192.168.1.24`)
   - macOS: `ipconfig getifaddr en0`
   - Linux: `hostname -I`
3. On the phone, open `http://192.168.1.24:3000` in the browser.

If it does not load, allow the port through the firewall:

```powershell
# Windows (admin PowerShell), only for the local network
netsh advfirewall firewall add rule name="AIBA 3000" dir=in action=allow protocol=TCP localport=3000
```

```bash
# Linux
sudo ufw allow 3000/tcp        # remove it again when you are done testing
```

Keep `COOKIE_SECURE=false` for plain `http://` (that is the default), and add your
own values; on a phone the dashboard is usable, and the layout switches to the
mobile drawer below `lg`.

### Method 4 — a temporary public link, without renting a server

Cloudflare Tunnel gives you a real `https://…` address pointing at the app on your
own computer — free, no account needed for a quick tunnel. Handy for showing the
console to someone else today.

```bash
# 1. install the tunnel client (once)
#    macOS:  brew install cloudflared
#    Linux:  https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/
#    Windows: winget install --id Cloudflare.cloudflared

# 2. start AIBA
npm run agent

# 3. in a second terminal, start the tunnel
cloudflared tunnel --url http://localhost:3000
```

cloudflared prints a URL like `https://random-words-1234.trycloudflare.com`. Open
it in any browser (also on your phone). Set `APP_URL` to that URL so email links
and redirects point at the right place, and keep `COOKIE_SECURE=true` because the
tunnel is https.

The same idea with other tools: `ngrok http 3000`, or `npx localtunnel --port 3000`.

Honest caveats: the link exists only while both processes run, the URL changes on
every restart (a named Cloudflare tunnel or ngrok domain is fixed but needs an
account), and anyone who has the link can reach the login page — so keep
registration closed (`ALLOW_REGISTRATION=false`) if you share it.

### Method 5 — GitHub Codespaces (runs in the cloud, nothing installed locally)

1. Open the repository on GitHub → green **Code** button → **Codespaces** tab →
   **Create codespace on main**.
2. When the editor opens, run in its terminal:

   ```bash
   npm install
   npm run agent
   ```
3. Open the **Ports** panel → find port **3000** → right-click → *Port Visibility*
   → **Public** → then click the globe icon (*Open in Browser*).
4. That forwarded URL is a normal https address you can open anywhere; sign in to
   the app there.

Notes: the Codespace pauses when you close it (free tier has a monthly hours
allowance), the database lives on the Codespace disk so it persists across
restarts of that same Codespace, and `APP_URL` should be set to the forwarded URL
if you want working email links.

### Method 6 — Google Cloud Shell (free, browser-only, and it has internet)

Cloud Shell is a free browser terminal with a public web-preview proxy, which
means the research sources and AI calls that are blocked in an offline sandbox
will work here.

1. Open <https://shell.cloud.google.com> (sign in with a Google account).
2. Clone and start on the proxied port:

   ```bash
   git clone https://github.com/humaidhanaan000-cyber/My-portfolio.git aiba
   cd aiba && npm install
   PORT=8080 npm run agent
   ```
3. Click the **Web preview** icon in the Cloud Shell toolbar → *Change port* →
   **8080** → *Change and preview*. The app opens in a new tab at a
   `https://8080-cs-….cloudshell.dev` address.

Notes: keep the Cloud Shell tab open (sessions idle-timeout and the VM is
recycled after ~20 idle minutes), so treat it as a demo/handover environment
rather than a production host. Same `APP_URL`/`COOKIE_SECURE=true` advice as above.

### Method 7 — Replit (cloud, browser-only)

1. <https://replit.com> → **Create** → **Import from GitHub** → paste
   `https://github.com/humaidhanaan000-cyber/My-portfolio`.
2. In the imported repl's shell: `npm install && npm run agent`.
3. Replit's webview opens on port 3000 (set it in the repl's *Webview* settings if
   it does not). Use the repl's public URL to open the console from any browser.

Notes: the free tier sleeps when idle, which pauses the scheduler; PGlite keeps
the data on the repl's disk.

### Method 8 — the permanent options (repeat, because they are the real answer)

If the goal is "a link I can open on any device, at any time, with the agents
actually running while my PC is off", only these do it:

- **VPS + Docker Compose** (§1) — full control, ~€5/month, your own domain.
- **Render Blueprint** (`render.yaml`, §2) — no server administration.
- **Railway / Fly.io** (§3) — same image, different host.

Everything in methods 1–7 stops when the machine or session stops. That is a
property of where the code runs, not a limitation of this application.
